# PDPA / Legal Review Checklist — จุดที่มนุษย์และทนายต้องตัดสิน

> ROADMAP 4.1 กำหนดว่า "ต้องมีมนุษย์/ทนายร่วม — Claude Code เตรียมร่าง+จุดที่ต้องตรวจ"
> ไฟล์นี้คือรายการนั้น เรียงตามความเสี่ยง ร่างเอกสารอยู่ที่ PRIVACY_POLICY_DRAFT.md และ TERMS_DRAFT.md
> ทุกข้อมีช่อง ✅ ให้ติ๊กพร้อมชื่อผู้อนุมัติและวันที่

## A. เรื่องที่บล็อกฟีเจอร์อยู่ (ตัดสินใจก่อนเปิดใช้)

- [ ] **A1 — Cold outreach (Phase 2.2):** การส่ง RFQ ไปยังอีเมล/LINE ของผู้ขายที่**ยังไม่ได้สมัคร** ใช้ฐานกฎหมายอะไร (ประโยชน์โดยชอบ vs ต้องขอความยินยอมก่อน)? ต้องมีข้อความ opt-out อย่างไร? แหล่งที่มาของ contact ต้องเป็นแบบไหนถึงใช้ได้ (ห้าม scrape — กติกาข้อ 5 ฝังในระบบแล้ว แต่ contact ที่ผู้ออกแบบกรอกเองถือเป็นอะไร)?
  → จนกว่าจะตอบข้อนี้ ระบบส่งเฉพาะ in-app ให้ผู้ขายที่สมัครแล้วเท่านั้น (สถานะปัจจุบัน)
- [ ] **A2 — Silent account creation (2.3):** แผนเดิมให้ผู้ขายที่ตอบ RFQ ครั้งแรกได้บัญชีอัตโนมัติ — สร้างบัญชีให้คนที่ยังไม่กด "สมัคร" ทำได้ภายใต้ PDPA เงื่อนไขไหน?

## B. เอกสารหลัก (ต้องเสร็จก่อน launch)

- [ ] **B1 — Privacy Policy:** ตรวจ/แก้ร่างทั้งฉบับ โดยเฉพาะ: ฐานกฎหมายของ analytics (ประโยชน์โดยชอบพอไหม หรือต้องขอ consent), ระยะเวลาเก็บข้อมูลทุกหมวด (ตอนนี้เป็น ⚠️ ว่าง), นิติบุคคลผู้ควบคุมข้อมูล
- [ ] **B2 — Terms:** ตรวจ/แก้ร่าง โดยเฉพาะ: สถานะทางกฎหมายของ "ใบเสนอราคาที่ถูกเลือก" (ผูกพันแค่ไหน — กระทบ dispute ระหว่างผู้ใช้), ข้อจำกัดความรับผิดที่บังคับใช้ได้จริงตามกฎหมายไทย, เขตอำนาจศาล
- [ ] **B3 — ถ้อยคำ consent ตอนสมัคร:** ปัจจุบันระบบมี checkbox "ยอมรับข้อกำหนดและนโยบายความเป็นส่วนตัว" + เก็บ timestamp — ทนายยืนยันว่าถ้อยคำ/รูปแบบพอ หรือต้องแยก consent เป็นรายวัตถุประสงค์
- [ ] **B4 — Cookie:** ระบบใช้เฉพาะคุกกี้จำเป็น (session + ภาษา) ไม่มี tracking ภายนอก — ยืนยันว่าไม่ต้องมี cookie banner หรือควรมีแถบแจ้งขั้นต่ำ

## C. โครงสร้างการปฏิบัติตาม (องค์กรต้องตั้ง)

- [ ] **C1 — DPO:** ประเมินว่าเข้าเกณฑ์ต้องแต่งตั้ง DPO ตามมาตรา 41 หรือไม่ (ประมวลผลข้อมูลจำนวนมาก?) + ระบุช่องทางติดต่อในนโยบาย
- [ ] **C2 — ROPA:** จัดทำบันทึกรายการประมวลผล (มาตรา 39) — ตาราง "ข้อมูลที่เราเก็บ" ในร่าง Privacy ใช้เป็นโครงตั้งต้นได้
- [ ] **C3 — Data Processing Agreement:** รายชื่อผู้ประมวลผลภายนอกทั้งหมด (hosting, email, LINE API เมื่อเปิดใช้, payment vendor เมื่อเลือก) + ทำ DPA กับแต่ละราย
- [ ] **C4 — โอนข้ามแดน:** ยืนยันที่ตั้งเซิร์ฟเวอร์/ผู้ให้บริการ ถ้าข้อมูลออกนอกไทยต้องมีมาตรการตามมาตรา 28
- [ ] **C5 — ขั้นตอนแจ้งเหตุละเมิด 72 ชม.:** วางผู้รับผิดชอบ + ขั้นตอนภายใน (ระบบมี audit log + error log ให้ใช้สืบสวนแล้ว — ดู docs/OPERATIONS.md)
- [ ] **C6 — ขั้นตอนรับคำขอใช้สิทธิ:** ช่องทางรับคำขอ (เข้าถึง/ลบ/แก้ไข/โอนย้าย) + SLA 30 วัน + ใครอนุมัติการลบข้อมูลที่พันกับบันทึกธุรกิจของอีกฝ่าย (เช่น RFQ ที่ผู้ขายตอบไปแล้ว)

## D. จุดที่ระบบรองรับแล้ว (ทนายรับทราบ ไม่ต้องสร้างใหม่)

- ✅ RFQ privacy: ผู้ขายไม่เห็น contact ผู้ออกแบบ (enforced + tested — กติกาข้อ 4)
- ✅ ขายข้อมูลเฉพาะ aggregate (กติกาข้อ 3) — หน้า performance เทียบเฉพาะค่าเฉลี่ยแพลตฟอร์ม
- ✅ รหัสผ่าน bcrypt(12), จำกัด 8–72 ตัว · rate limit ทุกจุดเสี่ยง · security headers
- ✅ Audit log ทุก mutation ที่แตะราคา/สเปก/สถานะ RFQ · analytics เก็บระดับ org ไม่มี PII ใน props
- ✅ Consent checkbox + `termsAcceptedAt` เก็บเวลายอมรับต่อผู้ใช้
- ✅ Backup + ขั้นตอน restore (docs/OPERATIONS.md)
